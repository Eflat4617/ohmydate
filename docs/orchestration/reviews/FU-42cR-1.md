Findings (most severe first):
  [MEDIUM] A client disconnect before the handler starts still settles the operation; the handler then runs untracked (violates the binding "a client disconnect does NOT settle it")
    Evidence: services/api/src/http/shutdown-context.ts:104-108 settles on socket 'close' whenever !handlerStarted; settleOperation (:48-51) deletes the requestOperations entry; the onRoute wrapper (:126-127) only marks an EXISTING record, so a handler that starts after that point is never re-tracked. Fastify 5.12.8 does not check for an aborted socket before calling the handler (lib/handle-request.js preHandlerCallback checks only reply.sent). Repro (tsx, in-process buildApp + production createApplicationClose(app, 12000, 2000), route with an async preHandler awaiting 200ms of simulated I/O, full POST body, client socket destroyed at 50ms): "135ms pendingOperationCount=1 / 185ms after client disconnect (preHandler running): pendingOperationCount=0 / 287ms handler started; pendingOperationCount=0 / 385ms close() starts / 385ms close() resolved (db destroy + exit 0 would follow) / 1288ms handler finished (mutation work done)", with no warn/error logs. This is the FU-42R2 failure class: a mutation runs while the DB is destroyed and exit 0 is reported. It is latent, not reachable today: production preValidation (routes.ts:613-640) only does in-memory session/CSRF work, so no macrotask falls between body completion and handler start. Any I/O-backed pre-handler step (a PG SessionStore behind the existing port, a DB rate limiter, an owner lookup) would silently bring back the persisted needs_reconcile/idempotency inconsistency, and no test would fail.
    Required change: when a handler starts, always hold a live operation. In the onRoute wrapper, if requestOperations has no unsettled record for request.raw, create and register a fresh one (meta from routeOptions) before calling the original handler; keep the socket fallback for handlers that never start. Add a real-socket regression: async I/O preValidation/preHandler, client disconnects during it, then close(). close() must wait for the handler (and exit 1 via the unsettled path if the handler ignores abort).
  [LOW] The wrapper turns a Reply-thenable rejection into an uncaught exception (process crash)
    Evidence: shutdown-context.ts:135-145. When a SYNC handler returns `reply`, isThenable() is true. Reply.prototype.then (fastify lib/reply.js:490-509) is callback-based and returns undefined, so the `throw error` at :143 escapes from the eos callback. Repro: a sync handler returns reply, then a timer does reply.raw.end('x') followed by reply.raw.write('y'). Stock Fastify: response 200, exit 0. Wrapped: exit 1, "shutdown-context.ts:143 throw error; Error [ERR_STREAM_WRITE_AFTER_END]". Not reachable in production: every registered handler is async, and the 404 handler is not routed through onRoute.
    Suggestion: chain through Promise.resolve(result).then(settle, settle-and-rethrow) so a rejection stays inside a promise that Fastify's wrapThenable handles; add a sync-returns-reply test.
  [LOW] A per-request socket 'close' listener emits MaxListenersExceededWarning when 11 or more requests are pipelined on one socket
    Evidence: shutdown-context.ts:107. Pipelining 15 GETs on one socket gives "MaxListenersExceededWarning ... 11 close listeners added to [Socket]"; --trace-warnings points at shutdown-context.ts:107:14. Listeners are removed on settlement, so this is not a real leak, but any client can trigger the warning.
    Suggestion: one close listener per socket (a WeakMap from socket to the set of unstarted operations).
  [LOW] Responses that complete during the cleanup window are cut off by closeAllConnections
    Evidence: main.ts:467-471. closeAllConnections() runs as soon as the last handler promise settles, before the error handler's or async onSend's response bytes are written. Compiled connected control (R2 repro with the client kept connected): the client got a transport TypeError, not 503 provider_unavailable. Compiled 13s abort-ignoring handler finishing at 12.9s: exit 0 but no 200 delivered. No data inconsistency: needs_reconcile=true, and idempotency was released or completed.
    Suggestion: once settled, wait for pending responses (waitForResponses) within the rest of the cleanup budget, then close the remaining sockets.
  [LOW] onClose hooks can run before draining handlers finish; the step-5 comment is inaccurate
    Evidence: main.ts:430 starts app.close() immediately. When every socket is already gone, Fastify runs onClose at once. Probe: "164ms close() start / 164ms onClose hook ran / 596ms handler done / 598ms close() resolved". Only reconciler.stop() is registered today (app.ts:441), which is harmless.
    Suggestion: correct the main.ts:469 comment, and document or enforce that onClose hooks must not release resources that handlers use.
  [LOW] SHUTDOWN_CLEANUP_BUDGET_MS is not bounded against the 15s deadline
    Evidence: main.ts:93-101 accepts any positive value. A value of 3000ms or more makes drain (12s) + cleanup reach the hard deadline, which then exits 1 before the unsettled log and before DB destroy.
    Suggestion: clamp to (SHUTDOWN_DEADLINE_MS - SHUTDOWN_DRAIN_BUDGET_MS - margin), or reject at boot.
