Findings (most severe first):
  [HIGH] A write whose response is lost after Vikunja applied it is never reconciled; the recurring completion record is lost
    Evidence: packages/provider-vikunja/src/task-repository.ts:497 (complete: patchTask has no reconcile handling) and :418/:430 (update sets remoteWriteApplied only after patchTask resolves, so a PATCH that throws counts as not applied). Fake-HTTP probe: PATCH done:true on a repeating task moved due_date upstream, then returned 502. Result: complete -> provider_unavailable; mapping needsReconcile=false; get -> version 1 with dueAt 2026-11-21 (already advanced); retry complete(v1) -> VersionConflictError "expected version 1 but found 1"; listChangedSince(null) -> [{version:2}] with NO completedOccurrenceAt. The ADR-016 §4 completion record is gone, and the retry after the next poll completes the following occurrence too. Same root cause in update: PATCH {title:"Ghost"} applied, then 503 or AbortError -> get shows "Ghost" at v1 with no journal entry, and update(v1) gets the same-version conflict until a feed poll reconciles to v2. This is the unknown-outcome part of R1 HIGH #2 ("partially applied remote mutations") and R1 HIGH #3.
    Required change: treat ProviderUnavailableError from a write (5xx/timeout/network) as outcome-unknown. Mark needsReconcile, and bump the version only if the remote ETag actually changed. In complete(), persist a pending-completion intent before the PATCH, so reconciliation emits completedOccurrenceAt when the provider shows done or an advanced occurrence. Add fake-HTTP tests for applied-then-5xx and applied-then-timeout on update and on recurring complete, plus a negative: a definitive 4xx must not mark reconcile or bump the version.
  [MEDIUM] (Required) Full resync after CursorInvalidatedError drops changes when the journal epoch changes but mappings persist
    Evidence: task-repository.ts:142 defaults journal to a fresh InMemoryChangeJournalStore while mappings/plannerFields are injected, which is exactly how test/contract.test.ts:52 wires it. change-journal-store.ts:37 names the in-memory journal for "the temporary API wiring". :578/:601: a null cursor reads only the current journal. domain errors.ts:82 prescribes listChangedSince(ownerId, null) + reconcile as the recovery. Probe: consumer drained through v3; v4 committed to journal J; repo rebuilt with the same mappings and a new journal. Old cursor -> CursorInvalidatedError (good), but listChangedSince(null) -> changes [] because reconcileRemote skips v4 (mapping ETag matches). The v4 change is never delivered.
    Required change: make the null-cursor resync complete after an epoch change. Example: on first use of an owner's fresh journal, append one snapshot entry per mapped live/deleted task at its current localVersion (the null path already lists all remote tasks). Or make a journal mandatory whenever mappings are injected and document it. Test: fresh journal + preserved mappings -> null cursor returns every live task.
  [LOW] Change cursors are not bound to an owner
    Evidence: task-repository.ts:564-590. The epoch is store-global and the sequence is per owner, so owner A's cursor is accepted for owner B when B's head >= A's sequence, silently skipping B's earlier entries. My probe was rejected only because B's head was 0. No cross-owner data exposure, since readAfter is owner-scoped.
    Suggestion: put ownerId (or a hash of it) in the cursor and invalidate on mismatch.
