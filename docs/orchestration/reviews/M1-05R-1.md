# M1-05R-1 (ctx_bf4bfacdf49a)

REVIEW VERDICT: REQUEST_CHANGES
Findings (most severe first):
  [HIGH] Existing change cursors silently lose future changes after repository restart
    Evidence: packages/provider-vikunja/src/task-repository.ts:127 and :498. The journal/sequence reset per instance, while cursor.q is accepted unchanged. A read-only stdin probe preserved MappingStore and PlannerFieldStore, performed two updates, consumed cursor {s:1767225600,e:"42",q:2}, constructed a new repository, and performed another update: get returned version 4/title "post-restart update", but listChangedSince(oldCursor) returned changes:[] and the unchanged q:2 cursor. The newly committed event at sequence 1 can never be returned through that cursor; remote reconciliation also suppresses it because the mapping already holds its ETag.
    Required change: make journal/cursor state restart-safe, or explicitly invalidate old-instance cursors and provide a reliable full-resync path. Document and test restart semantics; merely acknowledging volatile historical storage does not address silently losing future changes.

  [HIGH] A failed dependency write commits planner fields without a version or change event
    Evidence: packages/provider-vikunja/src/task-repository.ts:391. putTask runs before applyDependencyDiff and the final remote GET, mapping version update, and journal append. A fake-HTTP probe called update({priority:4,dependsOn:[existingDependency]}, expectedVersion=1) with relation POST returning 503: update rejected with provider_unavailable, but subsequent get returned priority:4, version:1, dependsOn:[], and listChangedSince(null) returned changes:[]. The observable task changed under the same version despite the failed call.
    Required change: stage planner-field writes until prerequisite remote operations succeed, and define recovery/reconciliation for partially applied remote mutations or a failed final GET. Ensure every observable committed planner-field change has a corresponding version and journal entry.

  [HIGH] Recurring completion has no usable planner completion record as required by ADR-016
    Evidence: packages/provider-vikunja/src/task-repository.ts:455 and :697; docs/blueprint/13-ADR.md:91. A live synthetic task configured through the public API with repeat_after:86400/repeat_mode:0 started todo, version 1, dueAt 2026-11-20T12:00:00.000Z. complete returned todo, version 2, dueAt 2026-11-21T12:00:00.000Z; subsequent get also returned todo even though PlannerFieldStore.status was done. resolveStatus discards that done value when Vikunja reopens the task, and the journal exposes only an undifferentiated TaskChange, so a consumer cannot observe the planner completion required as the source of truth.
    Required change: implement an observable planner completion record/event and reconcile the provider's reopened occurrence separately, as ADR-016 section 4 requires. Add the specifically required recurring-task test; coordinate a contract adjustment if that event needs an additional port.

  [MEDIUM] Valid dueAt values with nonzero milliseconds are rejected
    Evidence: packages/provider-vikunja/src/validation.ts:53 and :79. Date.UTC is constructed without the fractional part, then compared with Date.parse(original). Probe: domain isInstant("2026-11-20T14:59:00.123Z") returned true, while validateInstant on that value threw ValidationFailedError "impossible calendar date-time"; .000Z succeeded. The offset equivalent with .123+09:00 was also rejected by adapter normalization.
    Required change: retain supported fractional precision during calendar validation/normalization; cover fractional UTC and explicit-offset values, including negative impossible-date cases.

  [MEDIUM] Exhausted network errors escape the domain error model
    Evidence: packages/provider-vikunja/src/client.ts:437 and :445. A fetch fake throwing TypeError("fetch failed") produced GET {name:"TypeError",code:null,calls:3} and PATCH {name:"TypeError",code:null,calls:1}. The retry policy itself is correct, but the final error is not ProviderUnavailableError, contrary to the packet.
    Required change: normalize network failures to ProviderUnavailableError while preserving GET-only retries and avoiding secret-bearing underlying errors in outward messages. Cover exhausted GET failures and a failed write without retries.

  [MEDIUM] The 10-second timeout excludes response-body consumption
    Evidence: packages/provider-vikunja/src/client.ts:479 and :483. The abort timer is cleared immediately after fetch returns response headers, before response.text(). A real local HTTP probe sent headers immediately and completed its body after 200ms; a client configured with timeoutMs:50 and retries:0 successfully returned "slow body" after 210ms. A stalled body can therefore wait indefinitely even with the default 10s timeout.
    Required change: keep cancellation active through body consumption/parsing and translate body-stage transport/abort failures consistently; add a delayed-body test using a real HTTP stream or a signal-aware fake.
