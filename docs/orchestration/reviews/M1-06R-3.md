Findings (most severe first):
  [HIGH] ProviderUnavailableError now returns 500 instead of the contracted 503 (regression introduced in c2bd70b)
    Evidence: services/api/src/app.ts:134 has the new condition `if (problem.status >= 500)`. It catches the 503 that domainErrorToProblem maps from ProviderUnavailableError (services/api/src/http/problem.ts:125-131) and sends status 500. The body is self-inconsistent: {"status":500,"code":"provider_unavailable","title":"Internal error"}. Probe (scratchpad probe3.mts, isolated planner_test schema; the repo proxy throws new ProviderUnavailableError('vikunja')): GET /tasks/{id} -> 500 (declared for getTask: 200,304,400,401,404,503, so 500 is undeclared). PATCH /tasks/{id} -> 500 (key released, 0 idempotency rows; declared for updateTask includes 503 but not 500). At 0b8c673 this path returned 503: R2 probe "503 provider_unavailable ... released". This breaks the packet AC ("mapping DomainError codes -> statuses per contract (404/409/412/422/428/503 ...)") and 08 §1 ("503(provider/LLM)"; provider paths declare 503). The path is unreachable with M1 InMemory wiring. However, packages/provider-vikunja (already on base) throws ProviderUnavailableError on network or upstream failure (client.ts:155-157, 238, 445-447, 481, 496), so every Vikunja outage would surface as an undeclared, non-retryable-looking 500. No test covers 503 (grep: zero 503/provider_unavailable assertions in services/api/test). The new "unmapped DomainError" test cannot catch this, because its subclass is not instanceof ProviderUnavailableError.
    Required change: restrict the generic branch to the unmapped fallback, e.g. `if (problem.status === 500)` (or `problem.code === 'internal_error'`), so 503 keeps its status, title and code. Add a test that a repo throwing ProviderUnavailableError returns 503 provider_unavailable with problem+json and traceId on a read (getTask). Also cover a mutation (updateTask), asserting 503 and that the idempotency key is released (0 rows). Keep the existing unmapped -> 500 test.
  [LOW] trustProxy accepts only a boolean, and true trusts any client-supplied X-Forwarded-For
    Evidence: config.ts:23 and app.ts:87. Probe with limit 2 and a varied XFF on each login: trustProxy=false -> 401,401,429,429 (correct); trustProxy=true -> 401,401,401,401, so the limiter is bypassed by rotating XFF if anything reaches the API without the proxy. config.test.ts checks only the config value, not the app wiring.
    Suggestion: type it as Fastify's `boolean | string | string[] | number` and configure the tailnet proxy address or hop count (09 §5). Add an inject test of the limiter key under both settings.
  [LOW] Query coercion is hardcoded to `limit`
    Evidence: routes.ts:593-601. Probe: limit=5 -> 200, limit=abc/1.5/0/101/repeated -> 400, status=todo -> 200, status=bogus -> 400, /projects?limit=3 -> 200, body priority "4" -> 400. All correct for today's contract, which has only one numeric query field.
    Suggestion: derive the coercible fields from integer/number properties in route.query, so a future numeric query param does not silently 400.
  [LOW] releaseQuietly swallows release failures without logging
    Evidence: routes.ts:326-332 and 348. The original error is rethrown correctly (error-handling.test.ts FlakyStore: 422 dependency_cycle, releases=1). If release itself fails, though, the row stays pending, so the key returns 409 for 24h (pending rows have no TTL) and nothing is logged.
    Suggestion: request.log.warn({ err }, 'idempotency release failed') with key metadata only.
  [LOW] The public BuildAppOptions.loggerInstance bypasses defaultLoggerOptions (redact paths and serializers)
    Evidence: app.ts:81-84. The option exists for tests, but a production caller passing an instance would lose the auth/cookie/csrf redaction. The pre-existing `logger` override has the same property.
    Suggestion: document it as test-only, or apply redact/serializers to the supplied child logger.
  [LOW] R1/R2 items acknowledged and still open: remove() reads the full change feed (needs a port change); replay x-trace-id header vs the stored body traceId, with sequential req-N ids (prefer UUIDv7); limiter and session maps never pruned; /api/v1 prefix vs root registration; task.deleted missing from the 08 §5 topic list; cookie Max-Age fixed while the session slides; a complete() failure after a successful in-memory mutation loses the outbox event (documented TX boundary).
