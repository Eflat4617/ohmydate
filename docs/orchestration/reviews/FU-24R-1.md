Findings (most severe first):
  [HIGH] New quadratic CPU / event-loop DoS in redact() (base is linear on the same inputs)
    Evidence:
      (1) privacy.ts:440-456 shorterEndAfter
        - It compiles a new non-sticky 'g' RegExp on every end-side rejection.
        - When no shorter match exists at `start`, exec() scans and backtracks at every later '+' to the end of the input, so the cost is O(#'+'^2).
        - Probe ('+' + 20 digits + ' ') repeated, head vs base: 25KB 1.7s, 50KB 7.0s, 100KB 30.5s, 200KB 99.4s. Base: 1-5ms.
        - Probe ('+1 ' + 20 digits + '\n'): 100KB 8.6s, 200KB 28.7s (base 4-5ms).
      (2) privacy.ts:286-309 + :517-522
        - The \b was removed from the API-key regexes, and a rejected match retries at start+1. A key-like token preceded by a word char now greedily matches to the end of its run at every occurrence before the start check rejects it.
        - Probe 'xsk_'x25K: 100KB 1.6s, 200KB 5.0s (base 1.0ms).
        - 100KB of 'axoxb-' 1.8s; 'aglpat-' 0.8s; 'xgithub_pat_' 0.4s (base <=1ms).
      Existing perf tests stay green because none of them uses these shapes, so the claim "perf met" does not hold for adversarial input. Fastify's default body limit is 1MB.
      Proof of root cause for (1): in a /tmp copy, adding the 'y' flag to the shorterEnd RegExp gives 30.5s -> 20ms and 8.6s -> 9ms, with 0 output diffs on a 20K random +cc corpus.
    Required change:
      - Make shorterEnd sticky ('y') and compile it once.
      - For word-boundary patterns, apply the start-side check before scanning the body. For example, find candidate starts with a prefix-only regex, check wordBoundaryBefore, then run a sticky full match only at accepted starts.
      - Add >=100KB perf tests for both shapes ('+'+20 digits repeated; 'xsk_' repeated).
  [MEDIUM] Recall regression vs base: the original-char word rule treats fullwidth Latin letters and digits as non-word
    Evidence: privacy.ts:211-215. isOriginalWordChar is false for every non-ASCII char. This is inconsistent with isBoundaryChar (:92-99), which keeps fullwidth digits as digits.
      - A key that starts with a fullwidth char is rejected whole. Head leaks each of these with report [], and base masks them:
        'ＡKIAABCDEFGHIJKLMNOP', ' ＡKIA…', 'ｓｋ－ａｂｃｄｅｆｇｈ１２３４５６７８', 'key: ｓk-abcdefgh12345678', 'ｇhp_'+24a, 'Ｂearer abcdefgh.abcdefgh.abcdefgh', 'ｘoxb-1234567890ab', 'ＡＩza…'.
      - trimmedWordEnd (:423-437) trims trailing fullwidth chars off the mask:
        'sk-abcdefgh１２３４５６７８' -> '[REDACTED_API_KEY]１２３４５６７８'; 'AKIAABCDEFGHIJKLMNO５' -> '[REDACTED_API_KEY]５'. Base masks both fully.
    Required change:
      - Count the fullwidth ASCII-variant word chars as word chars: U+FF10-FF19, FF21-FF3A, FF3F, FF41-FF5A (the FF01-FF5E rule R3 prescribed).
      - Add regressions for the inputs above.
  [LOW] AIza{30,40} no longer backtracks to an inner boundary
    Evidence: privacy.ts:302 + :423-437. The trim only removes trailing non-word chars, while JS \b would backtrack the quantifier.
      - 'AIza<35>-AIza<35>': the first key leaks (base masked both).
      - 'AIza<35>-suffixlong': the whole key leaks with report [] (base masked the key).
    Suggestion: retry shorter lengths for bounded patterns, or add a sticky backtracking variant like shorterEnd.
  [LOW] The shorterEnd lookahead (?![0-9０-９]) (:352) runs on the normalised copy, not on original chars (item 3's rule), so the last group can stay unmasked
    Evidence:
      - '+44 7402 3580 7649 611⑳' -> '[REDACTED_PHONE] 611⑳'
      - '+1 23 372 187 567⑳' -> '[REDACTED_PHONE] 567⑳'
      - '+82 10 1234 5678<ZWSP>12345' -> '[REDACTED_PHONE] 5678<ZWSP>12345'
      Base leaked these whole, so this is an improvement, but it is partial.
    Suggestion: walk the candidate ends and test each with boundaryAfter().
  [LOW] notWordPlusBefore (:253-267) treats a stripped char between '+' and the cc digits as a start boundary
    The higher-priority 82-prefix pattern then claims an inner sub-span, and the full +cc span is dropped by the covered check (:524-531).
    Evidence:
      - '＋<ZWNJ>82 8916 3731 8561,' -> '＋‌[REDACTED_PHONE] 8561,' (base masked all).
      - '+<U+180E>82 8288 2502 1185 9312 876233' leaks '1185 9312'.
    Suggestion: skip back over stripped chars for the '+' test only, or merge overlapping spans instead of dropping them.
  [LOW] The repo fuzz can only detect whole-token leaks
    Evidence: privacy.test.ts:672 `fold(result.text).includes(core)`. The 345 partial leaks below pass this test.
    Suggestion: assert coverage of every core character, from spans or by alignment.
