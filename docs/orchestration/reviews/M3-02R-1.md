Findings (most severe first):
  [HIGH] Generator ignores `now`: it places new blocks in the past and does not keep past/in-progress existing blocks fixed (packet: "keep locked/past/in-progress blocks fixed"; 06 §7)
    Evidence: generate.ts never reads input.now (only validate.ts:839 parses it). The placement window is max(horizon.start, earliestStartAt, dependency end) at generate.ts:337-341. Probe P1 (UTC, Mon 09-17; now=12:00Z; existing A 10-11 [past], A 11:30-12:30 [in progress], B 14-15): returned front_loaded feasible=true with A 09:00-11:00 and B 11:00-12:00. Every block is before now, both past/in-progress existing blocks are gone, changedBlocks=5. Random harness: 599 of 1556 feasible candidates had blocks starting before now (in every run where now > horizon.start).
    Required change: fix existingBlocks with start < now like locked blocks, and clip new placements to max(horizon.start, now) (or require horizon.start >= now in validateInput and still fix past/in-progress existing blocks). Add unit and golden tests, including a negative.
  [HIGH] Change minimisation (S5 x3) has no real effect; the G04 expectation "only conflicting blocks move, changedBlocks minimal" is not met, and the G04 fixture does not exercise it
    Evidence: existing blocks only feed objectiveScore (generate.ts:1271-1293). Greedy placement ignores them. improvePlacements only tries +/-30 and +/-60 minute shifts inside the same slot (generate.ts:1175), so most existing positions are unreachable.
    Probe R1 (UTC, Mon 09-17; A/B/C 60 min due 17:00; valid existing A 09-10, B 11-12, C 14-15; a commitment at 11-12 hits only B): front_loaded changedBlocks=4 (B and C moved); focus_blocked changedBlocks=4 (A and B moved). The ideal is 2. With no input change at all (no commitment), front_loaded still moves C (changedBlocks=4).
    Probe R2 (136 feasible replans: a policy's own previous plan plus one commitment over one of its blocks): changedBlocks p50=4, p90=8, max=10; 32 of 136 exceed the spec bound of affected+2.
    Probe R3 (existing plan from balanced, replanned with front_loaded/focus_blocked and nothing changed): median 100% of blocks moved.
    G04.json: the existing block 00:00-01:00Z and the commitment 01:00-02:00Z do not overlap, so this golden passes by coincidence.
    Required change: start placement from still-valid existing blocks and re-place only conflicting/affected tasks and their successors, then run improvement. Change G04 so the commitment overlaps an existing block, and assert changedBlocks <= affected+2 with untouched blocks retained. Add a negative test.
  [MEDIUM] Diversity dedupe ignores feasibility, so an infeasible candidate can suppress a feasible one
    Evidence: finalize() (generate.ts:1487-1499) compares candidates in request order regardless of feasible. Constructed case E1 (UTC, Mon 09-17; Z 420 min splittable 30-120 priority 1; Y 20 min non-splittable priority 4, due 17:00): balanced is infeasible (its 30-minute stride leaves 15-minute gaps) and focus_blocked is feasible at d=0.1477. generate(input, {policies:['balanced','focus_blocked']}) returns only balanced:false, with the note "1 distinct plan(s)... dropped as too similar". 7,500 random orderings did not hit this, but it is reachable.
    Required change: let feasible candidates win dedupe (an infeasible candidate must never drop a feasible one); add a test.
  [MEDIUM] inputHash does not cover the seed that was actually used
    Evidence: generate.ts:100-102 hashes `input`, but options.seed overrides input.seed. generate(inp, {seed: inp.seed+1}) produced different blocks in 70 of 1500 and 23 of 400 random runs, with the same inputHash every time. maxLocalImprovement also changes output and is not hashed.
    Required change: hash the input with seed replaced by the effective seed (plus maxLocalImprovement), or remove the override. Add a test that the hash changes with the seed override.
    Related (LOW): instants are not canonicalised. now='...00Z', '...00.000Z' and '+09:00' give three different hashes for byte-identical output (probe P3). Array order is also hashed.
  [MEDIUM] candidate.deficitMin is the capacity bound from deficit(), not the candidate's H7 shortfall
    Evidence: generate.ts:446 and 453 always use capacityDeficit(). In my harness, 925 of 1345 infeasible (non-input-rejected) candidates were short of required minutes yet reported deficitMin=0. G13 says "Placed 0 of 240" with deficitMin 0. A 50-task probe says "Placed 3720 of 4455" with deficitMin 0. 06 §3 H7 says a shortfall means feasible=false plus deficitMin.
    Required change: report each candidate's unplaced minutes as deficitMin (keep the capacity number as a separate field or explanation line), or get spec-owner sign-off on the capacity meaning.
  [MEDIUM] The published weights barely drive behaviour; policies differ through hard-coded ordering and slot rules
    Evidence: weights are read only in objectiveScore (generate.ts:1214), during the small-shift improvement step. Probe W1 (200 random inputs): swapping the front_loaded and focus_blocked weights changed 0 of 200 outputs; setting all weights to 0 changed 32 of 200. Outputs do differ between policies (all three identical in 190 of 1500 runs), but through orderTasks and selectPlacement, not the weights. So "published weights" plus POLICY_VERSION do not trace plan behaviour.
    Suggestion: score slot choices with the weighted objective, or document and version the ordering and slot rules as part of each policy.
  [MEDIUM] The generator property test is much narrower than 06 §10 and the packet
    Evidence: generate.property.test.ts:84-90 and SCENARIOS use at most 2 tasks and 1-day horizons. There are no dependencies, commitments, locked/existing blocks, exceptions, earliestStart, buffers or preferred windows, and breakAfter is fixed at 480. 06 §10 asks for up to 30 tasks and 21 days. "feasible implies validate()==[]" is a tautology, because generate derives feasible from that same call. Only maxDailyLoad is checked against the minute oracle.
    Required change: widen the input generator and check feasible candidates against an independent H1/H2/H6 minute oracle. My harness below does this and finds 0 violations.
  [LOW] balanced is infeasible on about 35% of inputs that front_loaded solves (134 of 386, all H7, mostly insufficient_available_time). Its priority ordering ignores due dates, and the 30-minute stride (generate.ts:685-703) fragments the day. ADR-006 allows this, but it feeds CP-SAT trigger (a); track it.
  [LOW] changedBlocks counts locked blocks. buildMetrics diffs state.intervals, which holds locked plus candidate blocks (generate.ts:1429-1452), while types.ts says "candidate blocks vs existingBlocks". A locked block missing from existingBlocks inflates the count. Align the doc and the code.
  [LOW] p90CoverageRatio ignores remainingMin: G08 is fully planned (120 of 120 remaining) but reports 0.333 (generate.ts:1462-1469).
  [LOW] Local improvement only shifts a block within its own slot (+/-6 or 12 cells). There are no adjacent swaps or merges (06 §4 step 4).
  [LOW] The FU-13 runaway-guard test covers only time.ts (transitions.test.ts:417-438). The validator's ORACLE_MAX_TRANSITIONS throw is documented but untested.
  FU-12: done. Validator date labels now come from toZonedDateTimeISO(timeZone) at the segment start, and the "independently" wording is gone (grep finds nothing).
