Findings (most severe first):
  [MEDIUM] A stale mapping put rewrites is_inbox. When another instance moves the marker, the cross-instance race turns into a raw 23505 and a 500.
    Evidence: PgMappingStore.put writes is_inbox from the caller's copy, in both the CAS UPDATE and the upsert patch (services/api/src/adapters/vikunja/pg-mapping-store.ts:93,110). markInbox (pg-mapping-store.ts:175-198) flips is_inbox without bumping local_version, so the CAS check (:126) cannot see a marker move. #ensureInbox re-reads after markInbox and then calls #bumpForKindChange (packages/provider-vikunja/src/project-repository.ts:200-207), which catches only VersionConflictError (:212-226).
    - Deterministic repro (scratch): two VikunjaProjectRepository instances share one PgMappingStore. A observes default X(10) and B observes Y(11). A is paused after markInbox(X)+get, and B.getInbox runs to completion. Result: B returns "Personal:inbox v2", and A REJECTS with DatabaseError code=23505 on "vikunja_mapping_owner_inbox_unique". Rows are [11*v2, 10v1].
    - Live two-process race: 1 of 115 trials returned POST /tasks 500.
    - Store level: a stale inbox=true CAS put gives 23505. A stale inbox=false CAS put succeeds and leaves the owner with ZERO markers. That second case is the update() path (project-repository.ts:389-404), which is unreachable today because there is no PATCH /projects route.
    - Scope: multi-instance only. composition.ts:50-63 shares one repository instance across routes and tasks, so in-process coalescing covers a single instance. A 5xx releases the idempotency reservation (routes.ts:323-329), so a retry succeeds.
    Required change (follow-up, before multi-instance): make markInbox the only writer of is_inbox (write it on INSERT only and drop it from put's UPDATE patch). Move the version bump into markInbox's transaction: local_version+1 for the promoted row unless it is fresh, and for the demoted row. CAS then detects marker moves. At minimum, catch 23505 in #bumpForKindChange and re-read.
  [MEDIUM] The first-create guard is last-writer-wins outside the transaction-overlap window, and the worker's residual is mis-described: the losing project is NOT unmapped.
    Evidence: markInbox clears any existing marker unconditionally (pg-mapping-store.ts:178-185), so the partial unique index only rejects truly overlapping transactions.
    - Live probe: two separate tsx API processes (buildApp PROVIDER=vikunja, PG planner_test, token with other:user), default-less synthetic accounts (default trashed, default_project_id=0), concurrent no-project POST /tasks, B staggered by 0-150 ms, 115 trials in total.
    - Every trial (115/115) had markerCount <= 1 and exactly one kind=inbox in GET /projects.
    - 90/115 trials left a duplicate Vikunja "Inbox". That happened in every trial with a stagger of 14 ms or less, and in none at 20 ms or more.
    - In 25/115 trials, B stole the marker after A had already answered, so A's task sits in the project that ended up normal.
    - The losing project keeps its mapping row (is_inbox=false), and GET /projects lists it as "Inbox:normal" next to the real Inbox, e.g. list=["Inbox:normal","Inbox:inbox"].
    Suggestion: either use a CAS markInbox(owner, entityId, expectedCurrent) that fails when the marker is no longer what resolution saw (then adopt the winner and trash the loser's freshly created, still-empty Vikunja project), or serialise the create path with an owner-scoped pg_advisory_xact_lock. Correct the residual wording in the ledger.
  [LOW] The demoted project's kind changes without a version bump, so AC3 is only partially met. The worker disclosed this.

T6 moves the Vikunja default to 5041 via JWT: "Inbox" becomes inbox v2 (bumped), but "Personal" goes inbox to normal and stays v1. The cause is that both markInbox implementations clear without bumping (mapping-store.ts:160-177, pg-mapping-store.ts:178-185). Impact is limited: there is no GET or PATCH /projects/:id route, and the web finds the Inbox by kind on every list. Fixed by the change in finding 1.
