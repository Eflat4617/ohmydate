Findings (most severe first):
  [MEDIUM] New recall regression: a match rejected by the post-hoc digit-boundary check skips the rest of its span, so PII that base and R2 masked now leaks with report [].
    Evidence: packages/llm/src/privacy.ts:326-328. On !overlapsDigitBoundary the loop re-execs from lastIndex=end. The old in-regex lookarounds retried at start+1 and backtracked.
    The following inputs are masked by both base 6d3f87e and R2 7292b4e. Head leaks them fully:
    (a) Start side:
      - "Room 3010 010-1234-5678", "No.1010 010-1234-5678", "사번 2019010 010-1234-5678", "1031 031-1234-5678".
      - Glued RRN behind a footnote marker: "①9001011234567", "⁰9001011234567", "㉑9001011234567". This is the glued variant of the R3-required class.
    (b) End side (the variable group count in the +cc pattern no longer backtracks): "+82 10 1234 5678 12345", "+1 415 555 2671 12345", "+82-10-1234-5678 / 12345", "+44 20 7946 0958 123456".
    Fuzz: 20,000 cases (17 seeds, random fullwidth, 20 default-ignorables, astral/㈜/U+FDFA/combining/CJK/circled/superscript neighbours). Head has 324 leaks, all class (a).
    In a /tmp copy, setting pattern.lastIndex = start + 1 before re-exec fixes all of (a): fuzz leaks 324 -> 0, and perf stays at 1-7ms per 100KB. It does not fix (b).
    Required change (follow-up):
      - Reset lastIndex to start+1 on rejection.
      - For (b), let the end check fall back to a shorter group count. One option: keep (?![0-9０-９]) inside the +cc regex as a second pass when the post-hoc check rejects.
      - Add regression tests for the inputs above.
