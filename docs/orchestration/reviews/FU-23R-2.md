Findings (most severe first):
  [MEDIUM] The Inbox marker is not single-valued. After a trashed default, renaming the planner-created replacement Inbox in Vikunja makes the next GET /projects create a third "Inbox". The renamed project, and its tasks, silently become kind=normal.
    Evidence: In packages/provider-vikunja/src/project-repository.ts:233-238, `.find` returns only the OLDEST marked mapping (pg-mapping-store.ts:155 orders created_at ASC). In practice that is the trashed original default, because project mappings never get deletedAt. :239-247 then falls through on deleted_at, and :250-262 adopts by title or creates. #ensureInbox (:186-205) marks a new mapping but never clears the old marker. Live probe T (buildApp PROVIDER=vikunja, file token, PG, synthetic user):
    - GET /projects returns [Inbox:inbox].
    - Token DELETE of the default sets default_project_id to 0.
    - GET /projects returns 200 [Inbox:inbox] (new ext 4116), and POST /tasks lands in 4116.
    - Rename 4116 to 'Personal' in Vikunja (no PATCH /projects route exists, so the Vikunja UI is the only rename path).
    - GET /projects returns ["Personal:normal","Inbox:inbox"]. A new Vikunja project 4117 'Inbox' was created, and the next no-project POST /tasks goes to 4117.
    - vikunja_mapping now has 3 rows with content_fingerprint='inbox' (4115, 4116, 4117).
    Control probe U (default cleared via JWT, project live, single marker): the rename keeps "Personal:inbox" and tasks stay in it. By code reading, restoring the trashed default from Vikunja trash also moves the identity back to the oldest marker, and kind changes without a version bump. Nothing is lost and there is no 503, but the worker's claim that a default of 0/missing/trashed "deterministically adopts the marked project" only holds while one marker exists.
    Required change (follow-up, non-blocking): keep at most one marker per owner. Clear the marker on the owner's other project mappings when #ensureInbox marks one, or try every live marked candidate newest-first before title adoption. Add a FakeHttp unit test: trash the default, get the replacement, rename the replacement, then getInbox returns it, POST /projects is never called, and the list shows exactly one inbox.
  [LOW] GET /user failures are swallowed completely, including transient 5xx/network errors, not only 401 provider_auth.
    Evidence: project-repository.ts:216-221 (`catch {}`). By code reading: on an owner's first getInbox, when the Vikunja default project is not titled "Inbox", a transient GET /user failure creates and marks a stray "Inbox". The next successful call resolves the real default, and the stray becomes normal.
    Suggestion: swallow only ProviderUnavailableError with reason==='provider_auth' (missing other:user). Rethrow everything else so it surfaces as 503.
  [LOW] Cost on the fallback path. Default-less accounts and tokens without other:user scan every owner mapping (task rows included) via listByOwner on each getInbox/get/list/update (project-repository.ts:233). GET /projects also resolves twice (ensureInbox + list): 2x GET /user, 2x listByOwner and listAllProjects. This is fine at personal scale. A dedicated indexed column makes it O(1) (see judgment below).

  JUDGMENT, inbox marker in content_fingerprint: ACCEPTABLE AS AN INTERIM for FU-23, NOT as the end state. Plan a dedicated column (migration 0004) as a follow-up.
    Why it is acceptable now:
    - Nothing else writes or reads fingerprints on project mappings (grep: every writer in task-repository.ts is task-only).
    - The snapshot, reconcile and planner-field paths filter entity_type='task'.
    - VikunjaProjectRepository.update spreads the base mapping, so the marker survives.
    - PG round-trip verified (probe rows show 'inbox').
    - No contract change.
    - services/api/migrations/ is outside FU-23 ALLOWED PATHS anyway.
    Why it should move:
    - (1) No DB invariant of at most one inbox per owner. The MEDIUM above accumulated 3 marked rows.
    - (2) The first-create race across API instances is not DB-guarded on default-less accounts. Two processes can each create and mark a different Vikunja project, and the PG unique constraint is only on (entity_type, external_id). In-process coalescing covers only one process.
    - (3) 0003 documents the column as the FU-16 reconcile tie-breaker. Any future project-level fingerprinting would silently erase the Inbox identity.
    - (4) The listByOwner scan described above.
    Proposed 0004:
    - is_inbox boolean NOT NULL DEFAULT false, with CHECK (NOT is_inbox OR entity_type='project').
    - Partial UNIQUE index on (owner_id) WHERE is_inbox.
    - Backfill from content_fingerprint='inbox' (one live row per owner), then NULL the fingerprint.
    - MappingStore gets an `inbox` flag and an owner lookup.
    - Update the MIGRATION_FILES pin and the rollback assertions.
    Do it together with the MEDIUM fix, before any multi-instance deployment.
