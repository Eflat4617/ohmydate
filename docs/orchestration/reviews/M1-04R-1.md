Findings (most severe first):
  [HIGH] Mapping uniqueness is weaker than the packet and database specification
    Evidence: services/api/migrations/0001_init.sql:125 and :127 add owner_id to both unique keys, whereas 04 section 3 requires UNIQUE(provider,entity_type,external_id) and UNIQUE(entity_type,entity_id,provider). A real-PG probe in an isolated planner_test schema inserted owner A/task A/vikunja/412, then owner B/task B/vikunja/412 successfully; owner B/task A/vikunja/413 also succeeded. Output: "Duplicate external ID across owners accepted: true" and "Same local entity mapped under other owner accepted: true". A single provider object or local UUID can therefore have conflicting mappings and version/ETag state under different owners, defeating the specified one-to-one identity contract.
    Required change: restore the two specified unique keys without owner_id and add negative tests for both cross-owner cases. An owner-scoped redesign requires an explicit specification decision; adding owner_id does not itself enforce ownership of entity_id.
  [MEDIUM] Required outbox payload is optional in the exported Kysely insert type
    Evidence: services/api/src/db/types.ts:25 defines Jsonb insert values with undefined and :122 reuses it for outbox_event.payload, but services/api/migrations/0001_init.sql:157 declares payload jsonb NOT NULL with no default. An in-memory TypeScript program assigning {id,owner_id,topic} to Insertable<OutboxEventTable> produced 0 diagnostics; the corresponding real-PG insert failed with SQLSTATE 23502, column payload. A caller can compile a normal event insertion that fails only inside the transaction at runtime.
    Required change: distinguish required JSONB columns from defaulted JSONB columns so payload must be provided, and add a compile-time negative test for its omission.
  [MEDIUM] The schema parity test does not validate the actual Database field types
    Evidence: services/api/test/db/types.test.ts:41 compares information_schema only with the independent databaseTables manifest. services/api/src/db/types.ts:326 and :332 merely export boolean type aliases without requiring true, and those aliases compare keys rather than column value types. In a compiler-host-only probe, changing UserTable.id from string to number in memory still produced 0 diagnostics for the full API project; the runtime manifest and its database comparison remain unchanged. This does not meet the packet's promised Database-interface parity guard.
    Required change: enforce type assertions linking each Database column's selected and inserted types to the schema manifest, including nullability/default behavior, and verify the database metadata needed for those assertions. Include a regression check demonstrating that an intentionally incorrect actual interface type fails.
