Findings (most severe first):
  [HIGH] Seeded replanning finds no feasible plan in common replans that the same policy solves without existingBlocks (regression introduced in round 2)
    Evidence: prepareReplan treats an existing block as still valid if it fits a slot, has a valid session length and stays inside the task window (generate.ts:417-451). It never checks dependency order (H3). A task is marked affected only when a block is invalid or the task is over-allocated (generate.ts:460). When an estimate grows, the task's seeds stay and only the remainder is chunked (generate.ts:643). That remainder can be shorter than minSessionMin. It is also placed without regard to a seeded successor, because windowEndMs (generate.ts:672) ignores successors. Local improvement runs only when the greedy plan is already valid (generate.ts:731). There is no fallback without seeds.
      N10 (UTC, Mon 09-17). Task A grows from 60 to 90 minutes with minSessionMin 45; existing A 09-10. Every policy is infeasible with H5: "30-minute session outside [45, 120]". The same input without existingBlocks is feasible. This needs only one task and no dependencies.
      N6. A grows from 60 to 120 minutes; B depends on A; existing A 09-10 and B 10-11. All three policies are infeasible with H3, because A's extra hour lands at 11-12, after B. The fresh run is feasible.
      N5. A new dependency B->A is added; existing B 09-10 and A 11-12. All three policies return the old blocks unchanged and infeasible (H3). The fresh run is feasible.
      Random replan harness: 600 base plans, each replanned with the same policy and compared with the same input without existingBlocks.
        Estimate growth (06 §7 trigger "slack<0", the G09 case): 66 of 600 replans (11%) are infeasible where the fresh run is feasible. When the grown task has a successor the rate is 42 of 83 (51%). Codes: H3 33, H5 18, H7 11, H3+H5 4.
        Dependency added: 200 of 474 (42%).
      For scale, 06 §1 CP-SAT trigger (a) tolerates 2%. Before round 2, existing blocks only fed the objective, so these inputs behaved like fresh runs.
    Required change:
      (1) In prepareReplan, treat a seed as invalid when it starts before the last block of any dependency (seeded, fixed or locked), and propagate that to successors.
      (2) When a seeded task still has unplaced minutes, release that task's seeds and mark its successors affected. At minimum do this when the remainder is below minSessionMin or cannot fit before a seeded successor.
      (3) If the seeded candidate is still infeasible, retry with the violating tasks and their successors released, then with no seeds. Keep the first feasible result; S5 still scores retention.
      Add unit tests for N5, N6 and N10, plus a negative test that a no-change replan still reports 0 changes. Add a property that a replan is feasible whenever the same policy is feasible without existingBlocks, or one that reports a bounded rate.

  [MEDIUM] Past and in-progress existing blocks are audited and counted like locked blocks, so some replans become impossible or are silently short
    Evidence: buildContext adds every existing block with start < now to effectiveInput.lockedBlocks (generate.ts:331-357). validate() audits locked blocks for H1-H7 and exempts them only from the horizon check (validate.ts:45). generateForPolicy subtracts their minutes from taskRequiredMinutes, which is remainingMin when supplied (generate.ts:636-643). requirements.ts describes remainingMin as "Minutes a task still needs".
      Sick day. The user works A 09-10, then at 12:00 adds a full-day 'off' exception for today. Every policy is infeasible (H2 on the 09-10 past block), and no plan can fix it.
      N2. Availability is edited from 09-17 to 10-17 after a 09-10 past block. Every candidate is infeasible (H2).
      N3. A has remainingMin=60, a past block 09-10 and a future block 13-14; now is 12:00. The result is feasible=true with zero blocks: the 60 remaining minutes are never scheduled and the future block is dropped.
      N3b. The same input with remainingMin=30 is infeasible for every policy ("overallocated by 30").
    Required change: decide the contract, document it and test it. One option: past blocks are history. They still block time (H1, H6 daily load and breaks) but are not audited for H2/H4/H5 and do not count toward remainingMin. The other option: remainingMin explicitly includes minutes in fixed past and in-progress blocks; then document that in types.ts and requirements.ts for M5 callers. Add tests for the sick-day and N3 cases.

  [MEDIUM] The spec-scale property test almost never reaches a feasible candidate, so its independent oracle barely runs
    Evidence: generate.property.test.ts:559-563 (HEAVY_RUNS is capped at 150). I copied the test to /tmp and added a counter. Two runs gave 2 of 237 and 5 of 231 candidates feasible, from only 2 of 150 inputs each time. The H1/H2/H6 oracle checks ran only on those few. Every other candidate only asserts explanation.length > 0.
    Required change: tune the heavy generator so a meaningful share of candidates is feasible, and assert a minimum feasible count. For example, draw locked and existing blocks from a prior valid plan, keep sessions consistent with remainingMin and loosen capacity. Consider an env knob for more heavy runs. Until then my own harness covers the gap (see "Verified as correct").

  [LOW] Local improvement now tries only one +30-minute shift per new block (generate.ts:1519). Round 1 tried -60, -30, +30 and +60. The commit message does not mention the change.
    Evidence: W1. Setting all weights to zero now changes 1 of 200 outputs (32 of 200 in round 1). Swapping the front_loaded and focus_blocked weights changes 0 of 200. For front_loaded a later shift can never improve S1. The published weights are now close to documentation only; ordering and slotRule (now versioned in policies.ts) drive the plans.
    Suggestion: restore the earlier-position shifts for new blocks, or state in policies.ts that weights only break ties.
  [LOW] finalize() swaps a feasible newcomer in for an infeasible kept candidate without re-checking it against the other kept candidates (generate.ts:1838-1852). In principle that can keep two plans with d < 0.15. I saw no case in 6,000 random inputs.
    Suggestion: re-check after the swap, or drop the newcomer when it is close to a feasible kept candidate.
  [LOW] Perf gating: the root `pnpm run ci` run no longer asserts p95 (performance.test.ts:94). The packet allows this, and the package-scoped script still asserts it (verified below), so it is not a test weakening. The perf fixture still has no dependencies, commitments or existing blocks.
