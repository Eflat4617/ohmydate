Findings (most severe first):
  [HIGH] The succession window does not cover the repository call it fences: a replaced holder's in-flight create still writes to Vikunja after B takes over (duplicates, and deletes a completed approval's task)
    Evidence: intake-service.ts:904/1003 touch once and then make ONE repository call (tasks.create/update). That call is many sequential HTTP requests: task-repository.ts:243 marker list (>=1 page GET), :253 assertAcyclic (one GET per transitive dependency), :255 POST create, follow-up GET, :293 mapping put, :308 relation POSTs, and :324 rollback DELETE + permanent DELETE. vikunjaCallBudgetMs() (client.ts:129) = 3x10000+100+200 = 30300, the budget of ONE GET request. Its doc comment ("upper bound for one repository call") is false: with default clients (owner-accounts.ts:193), s2's POST can start up to about 60.6s after the touch and s6's up to about 180s. The lock AbortSignal is never passed into the repository/client, so nothing stops these requests. Note: this Vikunja uses the same PostgreSQL 18 server, so the event that kills the lock connection also slows Vikunja.
    Repro (live Vikunja + durable PG stores, scratchpad vitest probe, FakeClock modelling a >40s call, same technique as the worker's own test):
      P2: hold A's s2 create POST (after its marker list and acyclic GET), pg_terminate_backend A's lock backend. B inside the window gets 409 Retry-After 40 (correct). Advance the clock 40001ms: B gets 200 with 6 tasks. Release A's POST: A gets 503, but there are SEVEN remote tasks ("Probe step 2" twice: 21743 from B, 21748 from A). A's mapping put re-pointed s2's plannedId to 21748, while s3 is blocked by 21743, which is now unmapped, so the s3 dependency is silently lost.
      P6: hold A's s2 relation POST (mapping already persisted), kill the lock, advance 40001ms. B gets 200: approval completed, 6 created rows, B repaired s2 blocked=[s1]. Release A: its relation POST gets 409 (already exists), and A's create rollback runs DELETE /tasks/21786 -> 204 and DELETE /tasks/21786/permanent -> 204. Now only FIVE remote tasks exist and get(s2) returns null after a completed approval (data loss).
    Required change: fence each Vikunja HTTP request, not each repository call. Before every request (at least every POST/DELETE, including rollback) check the ownership signal + holder CAS/touch, e.g. an approval-scoped guard or AbortSignal (AsyncLocalStorage or create/update opts) that VikunjaClient.request checks before each attempt and passes to fetch. Alternatively impose a hard per-repository-call deadline so that no request can start after touch + PROVIDER_MAX_CALL_MS - (one request budget), and suppress rollback after ownership loss. Amend ADR-020 §7's budget definition accordingly (that is a port/ADR scope decision for the coordinator). Add live regressions for P2 (in-flight create past the window: exactly 6 tasks) and P6 (in-flight relation/rollback past the window: completed approval keeps 6 tasks).
  [MEDIUM] A 409 approval_in_progress that carries Retry-After is stored under the Idempotency-Key, so a same-key retry never makes progress
    Evidence: routes.ts:375 stores every 409/422 (now with the Retry-After header) per 08 §1. P7: A loses its lock and gets 503 (reservation released). A same-key retry gets 409 Retry-After 40. After the window, the same key still replays 409 "retry-after 40" (1 remote task); only a NEW key gets 200 with 6 tasks. The natural client flow (503, then retry with the same key) is therefore stuck for the idempotency TTL. The web client does not call draft:approve yet.
    Suggestion (follow-up): release the reservation for the transient succession 409 (as for 503), or document that clients must mint a new key; pin it with a test.
  [LOW] markStep's ownership check is not atomic with its write
    Evidence: pg-intake-approval-repository.ts:209-240 does SELECT (holder predicate) and then a separate UPDATE of intake_approval_step outside a transaction. A successor's begin can commit between the two, unlike complete(), which uses FOR UPDATE in its transaction.
    Suggestion: use a single UPDATE ... WHERE EXISTS(holder predicate), or a transaction with FOR UPDATE.
  [LOW] A repaired mapped step publishes its pre-repair version
    Evidence: intake-service.ts:972 pushes existing.version after tasks.update has already bumped it. P5 observed the s2 actual version as 2, while the task.created outbox event carries 1.
    Suggestion: use the task returned by update.

    Evidence: intake-live.test.ts swapped createVikunjaRepositories/owner-account token wiring for hand-wired repositories in all six live tests. Assertions are unchanged; this is a coverage note, not a weakening.
    Suggestion: keep one live test on the production composition.
