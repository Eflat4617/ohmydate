  [HIGH] Following the §7.1 contract, an in-progress or finished non-splittable task makes every candidate infeasible
    Evidence: §7.1 and types.ts:31-34/100-104 say remainingMin is the forward need and past/in-progress blocks are history. For a non-splittable task whose single block started before now, the forward need is 0. validate.ts:643-655 then fails H5 on any non-splittable task whose required minutes fall outside [minSessionMin, maxSessionMin], including required = 0, so remainingMin = 0 always fails.
      N16 (UTC, Mon 09-17, now 12:00; A is non-splittable 90 min, with an in-progress history block 11:00-12:30; B is a 60-min splittable task). All four ways a caller can express this fail:
        A.remainingMin=0 -> every policy infeasible: H5 "Non-splittable task "A" requires 0 minutes, outside [90, 90]". B 12:30-13:30 itself is fine.
        remainingMin omitted -> feasible=true, but A is scheduled a second time (A 12:30-14:00).
        A removed from tasks -> input rejected (unknown_task).
        A and its history removed -> B is placed 12:00-13:00, overlapping the work still in progress.
      R6' random harness: 600 base plans. Each replan moves now to the middle of the plan, sets remainingMin = required minus history, and changes nothing else. 398 of 600 (66%) are infeasible for every policy. All 398 have a non-splittable task with remainingMin = 0, and the only code is H5. The other 202 are 100% feasible, and 552 of 600 report changedBlocks = 0, so the seeding logic itself is sound.
      Round 2 counted history toward the task, so this case was feasible then. It contradicts §7.1 ("past blocks must not make candidates impossible") and the packet ("keep past/in-progress blocks fixed"). The only workaround is to pass such blocks as lockedBlocks. That is undocumented, and it brings back the H2/H4 audit that §7.1 removed (the sick-day case).
    Required change:
      In checkH5, a non-splittable task with required = 0 needs no block: skip the bounds check and flag any block that is present. Keep the generator consistent.
      Document in types.ts and requirements.ts that an in-progress block counts entirely as history, so callers send remainingMin = required minus history minutes (0 for an in-progress non-splittable task).
      Add N16 as a unit test, plus a negative test: non-splittable, remainingMin=0, one block placed -> H5.
      Add a property: when now advances, remainingMin is set to required minus history and nothing else changes, the result is feasible with changedBlocks = 0.
