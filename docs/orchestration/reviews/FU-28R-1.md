Findings (most severe first):
  [LOW] Lock-client 'error'/'end' listeners are now removed BEFORE client.end(). A server FATAL or socket error inside the end() window becomes an unhandled 'error' event, which crashes the process.
    Evidence: services/api/src/adapters/vikunja/reconciler.ts:139-141 (removeListener x2, then `await client.end()`). Base torgal/ohmydate:reconciler.ts:79-81 had the safe order: end(), then removeListener. In the graceful-end path (a normal sweep, and the non-leader path that every instance runs every tick), pg keeps the socket open until the server closes it. A FATAL ErrorResponse in that window goes through _handleErrorMessage with no active query, then emit('error') with 0 listeners.
    Probe end-window-probe.mts patches pg Client.prototype.end to run pg_terminate_backend on its own pid and wait 300 ms before the real end():
      after-sweep: uncaught "terminating connection due to administrator command" + "Connection terminated unexpectedly", error listeners at end() = 0
      non-leader: identical
    The natural window is about one RTT per tick per instance, so this only fires if a PG shutdown, failover or terminate coincides with it. The likelihood is very low, but the impact is a process crash, which FU-27 had just removed.
    Suggestion: keep the (now no-op) listeners attached until end() resolves. Set `sweeping = false` (or a `closing` flag) at the top of the outer finally so onError/onEnd stay silent, which also prevents the spurious logs the reorder was meant to avoid. Alternatively attach `client.on('error', () => {})` right before end(). Add a test that terminates the backend during end().
  [LOW] The lock connect is unbounded: no connectionTimeoutMillis. "app.close never hangs" holds for lock, probe and unlock, but not for connect.
    Evidence: reconciler.ts:69-75. The Client gets keepAlive, statement_timeout and query_timeout, but no connectionTimeoutMillis (pg default 0 = infinite). Probe S4 (proxy accepts TCP, never answers the startup): lock() was still "PENDING after 8000ms" and run() never ran, so reconciler.stop() / app.close() would wait the same way. A SYN blackhole self-bounds at about 127 s (tcp_syn_retries).
    Side effect: when that hung connect finally ended, the lock logger emitted "vikunja leader lock connection ended; aborting sweep", because `sweeping` starts true (reconciler.ts:78) although no sweep had started.
    Mitigating: ownerIds() runs on the pool first and is equally unbounded (pre-existing), so a hung DB blocks there before the lock connect.
    Suggestion: add `connectionTimeoutMillis: queryTimeoutMs`, and set `sweeping` only once the lock is acquired.
  [LOW] A partition WITHOUT a server-side kill stalls failover for the server's TCP keepalive time (safe, but liveness degrades).
    Evidence: probe S3, default timeouts. A's probe times out after 5003 ms and A aborts (aCalls=[o1], returns false). The server still holds A's session and its advisory lock (sessionAlive=true), so B.runOnce() returns false. On this server tcp_keepalives_idle=7200, interval=75, count=9, idle_session_timeout=0, so no instance can sweep for up to about 2h11m. Client keepAlive (10 s) only protects the client side.
    Suggestion: ask the server for keepalives on the lock session through startup options. tcp_keepalives_idle, tcp_keepalives_interval and tcp_keepalives_count are user-settable, e.g. options '-c tcp_keepalives_idle=30 -c tcp_keepalives_interval=10 -c tcp_keepalives_count=3'. Or document a server keepalive or tcp_user_timeout setting in the ops runbook (coordinator-owned).
  [LOW] The T1 regression assertion (input symlink swapped after the check) was dropped along with the readTextFile seam.
    Evidence: services/api/test/vikunja/wiring.test.ts:352. "still follows the input symlink and reads the verified file" no longer swaps the link. The old test "reads the resolved path so a post-check symlink swap cannot redirect it" asserted readPaths==[resolvedInside] after a swap. The behaviour is still correct: in token-probe T1 (link swapped right after realpath) the result is ACCEPTED bearer=tk-inside. Nothing pins it any more, though, which is a mild conflict with the contract's no-assert-weakening rule.
    Suggestion: re-add it with beforeTokenFileOpen (swap link -> outside, expect tk-inside, not tk-outside).
