  [HIGH] Background reconciler can regress the planner-SoR local_version and reuse versions (FU-22 CAS exposed but never used)
    Evidence: packages/provider-vikunja/src/task-repository.ts:1153 (#commitReconciled puts stale `mapping.localVersion + 1` with no precondition; same unconditional puts at :547 update, :655 complete, :717 delete, :299/:1138/:1268). services/api/src/adapters/vikunja/reconciler.ts:114 + app.ts reconciler.start() now run this path automatically every 5 min, concurrently with request handlers on the same repo/stores. Probe (scratchpad, live PG planner_test + Vikunja; gated getTask after the sweep had read the v1 mapping; user updates v1->v2->v3 meanwhile): mapping.localVersion after sweep = 2, get().version = 2 with title 'race v3', journal versions for the task = [1,2,3,2], update with If-Match 3 -> VersionConflictError; the next edit re-issues v3 for different content. This is not ADR-016's accepted best-effort *external* lost-update: it is a planner-internal race on the planner's own version SoR, which is exactly FU-22 (MEDIUM, target M1-10). M1-10 turns it from "client poll races a write" into a scheduled background writer.
    Required change: pass `{ expectedLocalVersion: <version read> }` on every non-create mapping put in the adapter (at minimum #commitReconciled, update, complete, softDelete, reconcile-settle/markNeedsReconcile); on VersionConflictError in the reconcile path re-read and skip/retry instead of surfacing it; add a deterministic regression test (gated or fake client) mirroring the probe. If the coordinator rules adapter wiring out of M1-10 scope, the minimum alternative is to ship the reconciler off by default (VIKUNJA_RECONCILE_INTERVAL_MS default 0) until FU-22 lands.
  [MEDIUM] PgChangeJournalStore caches a rejected epoch load forever
    Evidence: services/api/src/adapters/vikunja/pg-change-journal-store.ts:70-75 (`#epochPromise ??= this.#loadEpoch()` is never cleared on rejection). Probe: first epoch() on a schema without the tables -> rejected; after migrating that schema the SAME instance still rejects ('relation ... vikunja_journal_epoch does not exist'); a new instance succeeds. The single store built by buildApp would make every journal-dependent call (get/list/create/update/listChangedSince via ensureSnapshot/append) fail until restart after one transient DB error on first use.
    Required change: reset `#epochPromise` on rejection (e.g. `.catch((e) => { this.#epochPromise = undefined; throw e; })`) + a test.
  [MEDIUM] Token secret refs are unconstrained (env: any variable; file:/bare ref any path)
    Evidence: services/api/src/adapters/vikunja/owner-accounts.ts:88-106. `env:DATABASE_URL` (or any secret env var) would be sent as `Authorization: Bearer` to VIKUNJA_URL; file:/bare refs accept any absolute or `..` path readable by the process; parse errors echo keys of a foreign JSON file (:131). Cleartext never reaches PG/logs/errors (verified: VikunjaClient errors carry no token, reconciler logs only error.message, token refs only in PG), so this is defence-in-depth against whoever can write vikunja_owner_account, not a direct leak.
    Suggestion: allow only `env:VIKUNJA_TOKEN_*` names and file refs equal to VIKUNJA_TOKEN_FILE or realpath-contained in a configured secrets dir; drop the bare-path fallback; add negative tests.
  [MEDIUM] Mapping / planner-field / journal writes are separate statements now that they are durable
    Evidence: task-repository.ts:547->548->549 and :1153->1160->appendJournal. A crash after the mapping put and before the journal append leaves a bumped local_version that never appears in the change feed (snapshot_done=true, so no re-seed); cursor consumers silently miss it until the next edit. The in-memory reference had no durable state to diverge.
    Suggestion (non-blocking, FU): transactional unit-of-work hook across the three stores, or a reconcile check that journal-head version per task == mapping.local_version.
  [LOW] Reconciler pins a pooled connection idle-in-transaction for the whole sweep; stop() does not await an in-flight sweep
    Evidence: reconciler.ts:18-28 (db.transaction() wraps run(); the sweep makes N HTTP calls).
