Findings (most severe first):
  [HIGH] New quadratic CPU / event-loop DoS in the +cc fallback walk (base is linear on the same input)
    Evidence: packages/llm/src/privacy.ts:514-520 (shorterEndAfter walk), :36 (SEPARATOR is an unbounded '*'), :295 (CC_PHONE_SOURCE), :573-576 (call site).
      - When the greedy +cc match fails the trailing digit check and the sticky fast path finds no longer end, the walk steps back one code unit at a time from rawEnd.
      - At every position where boundaryAfter() is true, it slices and runs CC_PHONE_EXACT. Every position inside a separator run qualifies, and each test costs O(span).
      - The cost is therefore O(L^2) for one match. The claim that this walk is bounded to about 30 chars is false, because SEPARATOR has no length limit.
      - Probe: '+1 12 34' + N spaces + '5678' + '99999', single run, head vs base:
        - 25KB: 400ms vs 0.9ms
        - 50KB: 1.58s vs 0.4ms
        - 100KB: 5.8s vs 0.7ms
        - 200KB: 21.9s vs 2.1ms
        - 1MB: 573s (9.6 min) vs 6.8ms
      - The same blow-up occurs when the run is tab/newline, '-._/', U+3000 or U+2003, and with fullwidth '＋１ １２ ３４…' (100KB 4.9-7.6s).
      - It also occurs with '+1 12 34 56' + N spaces + '78999' (20KB 245ms).
      - Repeated 1KB units cost about 0.66ms each (101KB 67ms, already over the 50ms perf budget).
      - Base masks none of these (report []). The fix must therefore keep the new recall without the quadratic cost.
      - Root-cause proof in a /tmp copy:
        - Change: in the walk, skip any end whose last normalised char is not a digit or ')', since CC_PHONE_EXACT can only match there.
        - That leaves at most about 25 candidate ends.
        - Timings: 100KB 5.9s -> 2.4ms; 1MB -> 12.2ms.
        - Output diffs: 0 on 60,000 random +cc strings and 0 on my 20,400-case fuzz. The recall probe gives identical results.
    Required change:
      - Bound the walk to ends that finish in a digit or ')' (or an equivalent bound).
      - Add >=100KB perf tests for '+1 12 34' + long space run + '5678' + '99999' and for the '+1 12 34 56' + long run + '78999' variant.
  [LOW] Pre-existing perf asserts changed from a single run to best-of-5 (process: this packet allows "add/extend tests only", and AGENTS.md forbids weakening asserts)
    Evidence: packages/llm/test/privacy.test.ts:403-413, :425-426, :488-489.
      - The thresholds are unchanged, and a quadratic regression still fails all five runs. The change does remove the load flake R1 saw.
      - However, it relaxes the measured statistic of tests that existed in base.
    Suggestion: the coordinator should accept this explicitly, or limit bestOfFive to the newly added tests.
  [LOW] Glued RRN with a digit-folding marker in front leaks 1-2 trailing digits (pre-existing, identical on base)
    Evidence: my fuzz, 47 of 120,000 cases (33 leak 1 digit, 14 leak 2). Every case is an RRN with no separator, preceded by ⁰¹²³①⑳㉑, with an ignorable before the last digit(s).
      - Example: '⁰176７2<LRM>4５<RLM>19899<U+2069>6|' -> '[REDACTED_RRN]<U+2069>6|'.
      - The match starts on the folded marker, so its end lands on a stripped char, which counts as a boundary.
      - The repo fuzz never generates a separator-less RRN, so it cannot see this.
    Suggestion: when an accepted end is a stripped char followed by a digit, also try start+1. Or do not let a digit match start on an original non-digit char.
  [LOW] wordBoundaryAfter/Before return true at end/start of input unconditionally (privacy.ts:241, :257)
    Evidence: 'sk-abcdefgh12345678-' at end of input -> '[REDACTED_API_KEY]'. Base gives '[REDACTED_API_KEY]-', and JS \b would backtrack.
    This over-masks by one or two characters, which is privacy-safe.
    Suggestion: at the edges, return whether the adjacent char is a word char.
