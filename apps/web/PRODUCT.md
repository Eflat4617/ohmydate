## Platform

web

## Users

사용자는 제품 소유자 본인 한 명이다 (2026-11-13 본인 확인). 지금은 이 Ubuntu 노트북의
데스크톱 브라우저에서만 쓴다. Android PWA는 나중 일이고, 화면은 그때를 위해 좁은 폭도
계속 지원한다.

하는 일은 마감이 있는 목표(과제, 발표, 보고서 같은 것)를 실제로 끝내는 것이다. 하루에도
여러 번 들어와 "지금 무엇을 하면 되는가"를 확인하고, 집중 세션을 돌리고, 끝나면 짧게
회고한다. 계획을 세우거나 다시 세우는 일은 그보다 드물게, 한 번에 길게 한다.

장래에 여러 사용자가 쓸 가능성은 데이터 모델이 받아 두었지만(ADR-003), 지금 화면을
설계할 대상은 한 사람이다.

## Product Purpose

목표를 등록하면 맥락을 묻고, 단계로 나누고, 서로 다른 실행 가능한 일정안을 내놓고,
사용자가 승인한 일정만 반영하고, 실제로 걸린 시간으로 개인화하고 필요할 때 다시 계획하는
폐회로 개인 플래너다.

`목표 등록 → 맥락 수집 → 작업 분해 → 일정안 생성 → 승인 → 하루 수행 → 실제 시간 확인 → 개인화 → 재계획`

성공은 사용자가 지금 착수할 **하나의 다음 행동**을 쉽게 찾고, 마감 전에 일을 끝내는
것이다 (07 §1).

## Positioning

- 일정은 제안일 뿐이고, 승인 전에는 실제 일정이 한 줄도 바뀌지 않는다.
- 일정안은 하나가 아니라 성격이 다른 세 가지(앞당겨 끝내기, 고르게 나누기, 집중 시간
  묶기)로 나와서 비교하고 고른다.
- 추정은 내 실측 시간으로 보정된다. 집중 시간과 경과 시간을 따로 잰다.
- AI가 쓴 근거(어느 노트의 어느 구간)를 보여 준다. AI 없이도 조회와 직접 편집은 된다.

## Operating Context

- 매일: 오늘(다음 블록 확인, 수락·축소·재배치, 오늘의 약속과 오늘 마감) → 집중(타이머, 몰입 모드) → 회고(1탭 피드백).
- 수시로: 한달(달력 한 장에 블록·약속·마감, 날짜를 고르면 그날 목록). 장기 일정을 보면서도 오늘 할 일을 다시 확인한다.
- 가끔: 인박스에 빠른 추가, 계획 마법사(기본정보 → 유형 확인 → 질문 → 단계 초안 →
  일정안), 일정안 비교와 확정, 재계획 제안 검토.
- 설정: 가용 시간(주간 격자, 예외, 집중 한도), 약속, AI 설정, 레이아웃, 내 패턴.
- 노트: 계획에 근거가 되는 Markdown 노트를 목표·프로젝트·작업에 연결한다.
- 키보드: `n` 새 작업, `t` 오늘, `m` 한달, `f` 집중, `/` 검색, `?` 도움말.
- 화면 배치는 맥락에 따라 바뀐다(overview, planning, focus, deadline_risk, review, notes).
  전환 규칙과 안정성 규칙은 `docs/blueprint/07-ADAPTIVE-UI-SPEC.md` §2.

## Capabilities and Constraints

- Vue 3 `<script setup lang="ts">`, Pinia, Vue Query. Vue 파일에는 `<style>` 블록이 없고
  모든 스타일은 `src/styles/*.css`에 있다. `v-html` 금지.
- 문구는 전부 한국어 카탈로그(`src/i18n/messages/ko.ts`)에서 나온다. 화면에 문자열을
  직접 쓰지 않는다. 날짜·시간·기간은 `src/i18n/format.ts`를 거친다.
- 테스트와 E2E가 읽는 `data-*` 훅, 클래스 이름, 접근 가능한 이름, 키보드 경로는 계약이다.
- 네트워크 글꼴을 쓰지 않는다. 앱은 로컬에서만 돌고 오프라인에서도 열려야 한다.
- 용어: 오늘 · 인박스 · 작업 · 프로젝트 · 약속 · 가용 시간 · 집중 · 몰입 모드 · 일정안 ·
  블록 · 여유 · 위험도 · 축소 · 재배치 · 제안 · 확정 · 승인 · 회고 · 재계획 · 내 패턴.
  문장은 해요체, 버튼과 레이블은 짧게.
- 미결정: 폰에서의 실제 사용 방식(PWA 알림 포함)은 써 보기 전이다.

## Brand Commitments

이름은 OhMyDate다. 그 밖에 지켜야 할 시각 자산은 없다. 2026-11-13에 사용자가 색, 글꼴,
로고 마크, 화면 구성까지 전부 바꿔도 된다고 확인했다.

## Evidence on Hand

- 실제 화면과 합성 데이터: `VITE_MOCK=1`(MSW, `src/mocks`)로 모든 화면이 뜬다. 시각은
  2026-11-14 Asia/Seoul로 고정해 캡처한다.
- 화면 캡처와 접근성 점검 스크립트: `scripts/ui-screenshots.mjs`.
- 없는 것: 사용자 수, 후기, 수치로 된 성과. 만들어 넣지 않는다.

## Product Principles

1. 다음 행동 하나가 화면에서 가장 먼저 읽힌다.
2. 제안과 확정을 눈으로 구분할 수 있어야 한다. 승인 전의 것은 승인된 것처럼 보이지 않는다.
3. 시간은 이 제품의 재료다. 시각, 기간, 여유는 비교할 수 있게 정렬해서 보여 준다.
4. 화면은 하는 일에 따라 성격이 달라야 한다. 오늘, 계획, 설정이 같은 모양이면 안 된다.
5. 꾸밈은 일정 확인과 집중을 방해하지 않는 만큼만.

## Accessibility & Inclusion

WCAG 2.2 AA. 키보드만으로 핵심 시나리오를 끝낼 수 있어야 하고, 모든 조작 요소에 접근
가능한 이름이 있고, 의미를 색 하나로만 전하지 않는다(아이콘, 글자, 무늬를 함께).
`prefers-reduced-motion`에서는 움직임이 없다. 거친 포인터에서 터치 대상은 44px 이상.
axe critical/serious 위반 0.
